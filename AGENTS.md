# Инструкции для ИИ-ассистентов

Этот файл задаёт правила работы с проектом Spark. Перед изменениями изучай текущую реализацию и связанные документы: `Readme.md` описывает запуск и проверки, `api.md` — REST и WebSocket API, `фичи.md` — реализованные возможности и ограничения, `front.md` — frontend. Документация может отставать от кода: при расхождениях проверяй реализацию и не выдавай запланированную или описанную как ограничение функциональность за готовую.

## 1. Структура проекта

- `backend/` — Python backend на FastAPI.
  - `backend/api/v1/` — HTTP- и WebSocket-маршруты.
  - `backend/schemas/` — Pydantic-схемы запросов, ответов и событий.
  - `backend/db/dao/` — доступ к данным; `backend/db/models/` — ORM-модели.
  - `backend/core/` — прикладная логика и интеграции.
  - `backend/config/` — настройки.
  - `backend/infrastructure/redis/` — Redis и обмен сообщениями.
  - `backend/tasks/` — фоновые задачи Celery.
  - `backend/tests/` — unit- и integration-тесты.
- `frontend/` — React-приложение на Vite; исходный код находится в `frontend/src/`.
- PostgreSQL хранит данные, Redis используется для обмена событиями и очередей, Celery выполняет фоновые задачи. В проекте также используются Alembic, Ollama и S3-совместимое хранилище Yandex Cloud.

## 2. Архитектурные правила

- Маршруты в `backend/api/` отвечают за транспорт: разбор запроса, зависимости, вызов прикладной логики и формирование ответа. Не размещай в них SQL, ORM-операции или прямые операции с Redis.
- Все Pydantic-схемы размещай в `backend/schemas/`, а операции с БД — в DAO внутри `backend/db/dao/`. DAO не должны зависеть от FastAPI или выбрасывать `HTTPException`; преобразуй ошибки в HTTP-ответы на уровне маршрута или прикладной логики.
- Используй существующие модули `backend/core/`, `backend/infrastructure/` и `backend/tasks/` по их назначению. Не добавляй параллельные слои или новые абстракции, если задачу можно решить в текущей структуре.
- Для I/O в асинхронном коде используй асинхронные интерфейсы и `await`; не блокируй event loop. Соблюдай существующий способ запуска и интеграции фоновых задач Celery.
- Для Python обязательны аннотации типов аргументов и возвращаемых значений, включая `-> None`. Используй `PascalCase` для классов и `snake_case` для функций, методов и переменных.
- Сохраняй разделение frontend и backend. Поведение API и WebSocket сверяй с реализацией и `api.md`; учитывай явно описанные там расхождения и ограничения, прежде чем полагаться на соответствующий контракт.
- Не помещай секреты и реальные значения ключей в исходный код или документацию. Используй предусмотренные переменные окружения и шаблоны `.env.example` / `.env.test`.

## 3. Тесты и проверки

- Для нового или изменённого поведения добавляй целевые тесты в существующий набор. Новые методы DAO покрывай тестами; для интеграций с БД и Redis предпочитай интеграционные тесты и имеющуюся инфраструктуру Testcontainers, а не избыточное мокирование внутренних методов.
- Для backend придерживайся команд из `Readme.md`: тестовое окружение запускается через `docker-compose.test.yml` с `.env.test`; интеграционные тесты могут требовать Docker/Testcontainers. Ruff запускай из корня репозитория (`ruff check .` и `ruff format --check .`).
- Для frontend команды запускай из `frontend/`. Доступные проверки определяются в `frontend/package.json` (в частности, `npm run build`, `npm run lint`, `npm test` и `npm run typecheck`).
- После изменения проверь относящиеся к нему тесты и линтеры. Не изменяй несвязанные файлы и не исправляй посторонние проблемы в рамках узкой задачи.

## 4. Самопроверка перед завершением

1. Маршруты не содержат SQL, прямого доступа к сессии БД/Redis или локально объявленных Pydantic-схем.
2. Операции с БД находятся в DAO, схемы — в `backend/schemas/`, HTTP-ошибки — вне DAO.
3. Новое поведение проверено подходящими тестами; документация обновлена, если изменились описанные API, запуск или возможности.
